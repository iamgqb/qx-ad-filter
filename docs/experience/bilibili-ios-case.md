# 哔哩哔哩 iOS：商业卡片、开屏预加载与验证边界

2026-11-16，分析中文版哔哩哔哩 9.19.1（`tv.danmaku.bilianime`，build `91901100`），环境为 iPhone 12 / iOS 18.6.2、Quantumult X 1.8.1。新增 [bilibili-ad-filter.conf](../../rewrites/bilibili-ad-filter.conf) 1.0.0 与 [bilibili-ad-filter.js](../../scripts/bilibili-ad-filter.js)。国际版客户端不在本轮验证范围内。

## 可复用经验

- 普通内容也可能携带广告位和归因元数据。广告对象、卡片类型、跳转类型和画面需要交叉确认，不能仅凭字段名删除。
- 预加载素材与展示计划可能分开返回。只关联已确认的广告 ID，保留未知展示记录，避免把不明缓存语义当作已知协议。
- 投放计划处于未来时段时，连续冷启动没有广告不能证明开屏过滤有效。记录命中与画面验证的区别，不为构造结果而改写生产过滤器中的频控。
- 云端文件已写入、资源已下载和运行规则已执行是不同状态。同步故障时可在当前授权内使用独立临时资源采样，最终移除并切换正式订阅。

## 请求与处理依据

先按实际进程限量采集连接，确认候选 API，再通过 QX 原样放行的临时观察器采集路径和结构。第二阶段只保留首页与开屏的少量响应，原始材料放在项目外私有目录，仓库样本以示例标识、文案和域名重建。

| 实测接口 | 响应证据 | 正式处理 |
| --- | --- | --- |
| `app.bilibili.com/x/v2/feed/index` | `code: 0`，`data.items` 混合普通视频、直播与商业卡片 | 仅删除 `card_type: cm_v2`、`card_goto: ad_av / ad_web_s` 且 `ad_info.creative_content` 为对象的记录 |
| `app.bilibili.com/x/v2/splash/list` | `data.list` 的 22 条记录均含 `is_ad: true`，另有 `show`、空 `keep_ids` 和频控字段 | 保留广告 ID 与素材，以过期时间覆盖旧缓存；同 ID 展示计划一并过期，保留其他结构与间隔 |
| `app.bilibili.com/x/v2/splash/show` | 展示计划包含 `id`、`stime`、`etime`、`ad_cb`，与开屏投放链路对应 | 仅对实测 GET 使用原生 `reject-dict` |
| `/x/v2/splash/brand/list`、`/x/v2/splash/event/list2` | 品牌启动图资源、活动和账号容器 | 保留，不进入正式匹配 |

首页的一个普通视频同样有 `ad_info`，且 `is_ad_loc: true`；它没有商业素材对象，卡片仍为 `small_cover_v2 / av`。删除所有带 `ad_info` 的条目会误删正常视频，因此未采用。商品卡片和视频广告则分别出现 `cm_v2 / ad_web_s` 与 `cm_v2 / ad_av`，与推荐页推广内容对应。

仅 `app.bilibili.com` 进入正式 MitM。采样阶段出现的 `api.bilibili.com`、`cm.bilibili.com`、HTTPDNS、gRPC、图片和视频 CDN 均未据此新增拒绝规则。正式脚本不改写导航、账号或会员权限，不写存储、日志、通知，也不增加网络请求。

## 响应与缓存边界

脚本限定两个确切路径、GET、HTTP 200、JSON 成功响应及已知容器。未知格式、接口错误、解析失败和非空 `keep_ids` 原样放行。只有数据实际变化时才编码 JSON，回调恰好一次。

首页保持普通条目的顺序、`idx`、直播卡片、配置及其他字段，不自行重排分页标识。开屏保留 `max_time: 30`、`min_interval: 3600`、`pull_interval: 900` 等服务端参数；仅对已知广告记录设置 `begin_time: 1`、`end_time: 2`、`duration: 0`，并把同 ID 展示计划的 `stime`、`etime` 设为 `1`、`2`。这是已经过去的 Unix 秒级有效期组合；ID、素材、哈希及其他字段保留，用于覆盖旧缓存。未出现在广告列表中的展示 ID 保留；缺少已知时间字段的条目也不改写。

采样中既有未来投放计划，也有当日生效计划。一次按当日有效展示 ID 取得的单份素材，与连续截图中的「播客好友派」活动开屏一致，且该记录明确为 `is_ad: true`；它不属于品牌启动图接口。

最初清空 `list` 和关联 `show`，实际出现 `22 → 0`，但两次冷启动约 5.5 秒仍显示同一开屏，说明空数组未可靠使既有缓存失效。改用保留 ID、有效期过期的组合后，两次约 5.4 秒均进入正常首页。

短暂恢复真实预加载后未稳定复现该开屏，因此未把这组无广告画面当作完整的停用／启用对照。后续仅在独立诊断资源中临时缩短已观察到的间隔，并使用同一投放计划核对缓存；一秒及零间隔对照也未稳定复现，未据此扩大效果结论。已切回最终脚本并实际确认服务端间隔恢复；正式脚本没有重放或频控改写。长期频控、未被服务端再次下发的旧记录及其他投放形式仍有验证边界。

## 已完成的验证

- `npm test` 共 48 项通过。新增覆盖两类商业卡片、普通视频的广告位元数据、直播与混合值、展示 ID 关联、错误与未知缓存放行、单次回调、零诊断 I/O、URL 和 GET 边界、MitM 及远程脚本映射。
- 另用 6 份私有实测响应离线对照：首页 `10 → 8`，两份开屏列表各 22 条广告记录被设为过期；ID、素材、外层协议、正常条目及其他字段保持一致，品牌和活动接口原样放行。这些原始响应不作为仓库测试依赖。
- 使用独立临时包装核对首页实际执行：冷启动 `10 → 9`，翻页请求 `10 → 8`；最终过期版本实测 22 条记录保留 ID 并全部过期，关联展示计划分别有 3 条、1 条过期；记录的脚本哈希与仓库版本一致，`min_interval` 恢复为服务端的 3600 秒，两项临时采样存储键已清理。
- 冷启动后约 2.4、2.6、5.5、9.5 秒记录画面。约 5.5 秒仍出现带跳过倒计时的官方播客活动开屏，约 9.5 秒进入正常推荐页，原商品推广卡未出现；继续向下滚动两次，普通视频连续排列且下一页加载正常。这组画面解释了为何没有交付仅清空数组的方案。

这些证据区分了真实请求处理与单次没有广告的画面，不代表覆盖所有商业卡片、播放页、搜索、动态或未来版本。国际版及使用相同接口的其他客户端未回归；规则按请求匹配，其相同接口也可能受影响。
