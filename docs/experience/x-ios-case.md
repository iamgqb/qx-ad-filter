# X 原生 iOS App：代理证书拒绝与采集边界

## 结论与适用范围

2026-10-25，在 iPhone 12 / iOS 18.6.2、X 12.36（`com.atebits.Tweetie2`）、Quantumult X 1.8.1 上，未能通过 QX 的 HTTPS 解密与响应重写移除 For you 时间线广告。本次没有交付 X 过滤脚本或订阅资源。

这是上述环境下所测试路径的限制，不代表所有 X 版本、其他客户端或网页版都无法过滤。本次未开展网页版验证。

## 可复用经验

- 先证明能够取得解密响应，再编写依赖响应结构的过滤器。
- 加入 MitM 后正常功能失效时，对照连接日志与证书信任错误，区分采集失败和过滤逻辑失败。
- 日志中的域名与具体请求名称只能支持对应范围的判断，不能替代未取得的时间线响应。
- 撤回无效的诊断改动，保留版本边界；其他客户端或设备方案属于另行确定的范围。

## 实测证据

- 未加入 X 解密域名时，For you 时间线能展示正常推文和带 `Ad` 标记的广告。
- 临时加入 `api.twitter.com` 等 X 域名的 MitM 与限量观察规则，重新应用配置、重启 VPN 后，X 出现 `Posts aren’t loading right now`；观察器未取得可用时间线 JSON。
- 按 X 进程采集的连接信息包含 `api.twitter.com`，但连接域名本身不能证明接口路径或广告字段。
- X 的网络日志两次记录 `authChallengeMethod=NSURLAuthenticationMethodServerTrust`、TNL 错误码 `212` / `RequestOperationAuthenticationChallengeCancelled`，关联主机为 `api.twitter.com`，证书链为由现有本地 QX CA 签发的 `*.twitter.com` 证书。
- 日志中有明确错误名称的请求是同域名下的 `GrokAccountJwt`，不能据此声称已读取 HomeTimeline 响应或确定其广告结构。

这些证据说明原生 App 拒绝了本次 QX 代理证书，阻断发生在取得可改写响应之前；与证书固定或额外的服务端信任校验相符。未检查 App 的校验实现，不把某一种具体实现写成已证实事实。

## 后续处理

遇到相同版本和现象时，先检查信任挑战错误，不要重复编写尚无响应证据的广告字段过滤器。`skip_validating_cert` 作用于 QX 对上游服务器的验证，不能据此推断可以解除 App 对 QX 代理证书的拒绝。封锁共享 API 或图片域名也不能可靠地只移除混在时间线中的广告。

本次撤回临时规则和新增 hostname 后，配置与修改前备份逐字节一致，并重新应用配置、重启 VPN。临时观察脚本、抓包与原始日志已清理，仅保留本页脱敏摘要。

若需要继续，先与用户确定其他客户端或网页版等范围；不要把此失败自动扩展为替换 App、安装调试签名 App 或修改系统安全设置的授权。
